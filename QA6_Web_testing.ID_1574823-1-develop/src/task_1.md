# Задание 1. Клиент-серверная архитектура

## Интернет-банк "Т" 

### Блок-схема архитектуры 

1. Клиентское звено **Ключевое** (Frontend - React SPA / Мобильное приложение) 
   - Назначение: Обеспечивает пользовательский интерфейс (отображение баланса, истории операций, формы переводов). Собирает ввод пользователя, выполняет первичную валидацию (формат номера счета, сумма) и отправляет API-запросы к серверу приложений.

2. Балансировщик нагрузки **Ключевое** (Load Balancer - Nginx / F5)
   - Назначение: Распределяет входящие HTTPS-запросы от тысяч клиентов между несколькими экземплярами сервера приложений. Обеспечивает отказоустойчивость (если один сервер упал - направляет на живой) и проверяет "живучесть" серверов (health checks).

3. Сервер приложений **Ключевое** (Backend - Java Spring Boot / Node.js)
   - Назначение: Реализует бизнес-логику банка: аутентификация (проверка пароля/2FA), проверка достаточности средств, применение комиссий, формирование выписок, шифрование чувствительных данных. Взаимодействует с БД и кэшем.

4. Кэширующее звено (Redis / Hazelcast)
   - Назначение: Хранит в оперативной памяти временные данные для ускорения доступа: активные сессии пользователей (чтобы не проверять пароль каждый раз), курсы валют, часто запрашиваемые балансы счетов. Снижает нагрузку на основную базу данных.

5. Реляционная база данных **Ключевое** (PostgreSQL / Oracle)
   - Назначение: Постоянное, транзакционное хранилище критических данных: таблицы пользователей, счетов, переводов. Гарантирует ACID (atomicity, consistency, isolation, durability), чтобы при переводе денег они не потерялись и не продублировались.

6. Система очередей сообщений (RabbitMQ / Kafka)
   - Назначение: Асинхронная обработка длительных или фоновых задач. Например: генерация PDF-выписки по email, отправка push-уведомления о переводе, расчёт процентов по остатку. Клиент получает ответ "Операция принята" быстро, а реальная обработка идёт в очереди.

7. Система мониторинга и алертинга (Prometheus + Grafana / Zabbix)
   - Назначение: Собирает метрики со всех компонентов (время ответа, количество ошибок 500, заполненность диска БД). При превышении порогов отправляет алерт дежурному инженеру (через Telegram / PagerDuty) до того, как заметят пользователи.

## Сравнение подходов к резервированию

| Критерий | Горячий резерв (Hot Standby) | Холодный резерв (Cold Standby) |
| :--- | :--- | :--- |
| Готовность резервного сервера | Полностью включён, приложение запущено, соединение с сетью установлено. Готов принять трафик за секунды. | Выключен или работает без приложения. Требуется ручное включение, загрузка ОС и запуск сервисов. |
| Синхронизация данных | Постоянная (синхронная или асинхронная репликация в реальном времени). Потеря данных (RPO) стремится к нулю. | Периодическая (резервное копирование раз в час/день). Потеря данных = всё, что изменилось после последнего бэкапа. |
| Время переключения (RTO) | Секунды — минуты. Часто автоматическое (без участия человека). | Часы — дни. Требуется ручное восстановление из бэкапа. |
| Стоимость | Высокая: требуется 2x серверов, дополнительные лицензии, высокоскоростные каналы для синхронной репликации. | Низкая: один сервер + место для хранения бэкапов (обычно дешёвые HDD или облачное хранилище типа S3 Glacier). |
| Плюсы | • Почти незаметен для пользователя<br>• Минимальная потеря данных<br>• Автоматическое переключение<br>• Можно делать rolling update (обновлять компоненты по очереди) | • Очень дёшево<br>• Простота реализации (обычный бэкап)<br>• Хорош для некритичных данных<br>• Физически изолирован — защита от пожара/наводнения в основном ДЦ |
| Минусы | • Высокая стоимость<br>• Сложность настройки (split brain, кворум, синхронизация)<br>• Требует постоянного мониторинга<br>• Синхронная репликация может замедлять запросы | • Долгое восстановление (часы/дни)<br>• Гарантированная потеря данных (RPO > 0)<br>• Риск: бэкап может оказаться повреждённым<br>• Человеческий фактор при восстановлении |

## Cценарий теста для проверки отказоустойчивости при использовании "горячего" резерва

### Компонент тестирования - Реляционная база данных

| Действие тестировщика | Ожидаемый результат системы |
| :--- | :--- |
| Запустить мониторинг метрик | Все метрики в зелёной зоне |
| Начать запись логов балансировщика и приложений | Логи пишутся |
| Искусственно остановить сервис PostgreSQL на мастер-узле: `sudo systemctl stop postgresql` | Patroni обнаруживает недоступность мастера |
| Дождаться переключения | Replica автоматически повышается до мастера за <15 секунд |
| Продолжить выполнение тестовых операций | Балансировщик перенаправляет трафик на новый мастер. Клиенты видят кратковременную ошибку "504 Gateway Timeout" или задержку, но не потерю транзакций |
| Восстановить старый мастер-узел | Старый мастер подключается к кластеру как новая реплика (read-only) |
| Остановить тестовую нагрузку и собрать метрики | Все метрики зафиксированы |

Критерии успеха теста:
- Время переключения (RTO фактическое) ≤ 15 секунд
- Потеря данных (RPO) = 0 (ни одна успешная транзакция не потеряна)
- Автоматическое переключение произошло без ручного вмешательства
- После восстановления старого мастера кластер вернулся в состояние Active-Passive

## Метрики для отслеживания в тесте

| Метрика | Целевое значение | Что показывает |
| :--- | :--- | :--- |
| Время обнаружения сбоя (Detection Time) | < 5 секунд | Как быстро менеджер кластера понял, что мастер упал |
| Время переключения (Failover Time) | < 10 секунд | Интервал от падения мастера до начала работы нового мастера |
| Общее время восстановления (RTO) | < 15 секунд | Сколько времени система была недоступна для записи |
| Количество потерянных транзакций (RPO) | 0 | Потеряны ли данные? (при синхронной репликации = 0) |
| Процент успешных запросов во время теста | > 99.9% | Пользователи видели ошибки? |
| Split Brain флаг | Отсутствует | Не возникло ли ситуация "два мастера" |
| Время восстановления старого мастера как реплики | < 30 секунд | Кластер вернулся к исходному состоянию? |
